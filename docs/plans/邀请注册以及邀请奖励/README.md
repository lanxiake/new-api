## 一、需求概述

本次迭代包含三大功能模块：

### 1. 邀请注册强制校验（开关控制）
- 管理后台新增「**邀请注册**」总开关
- **开启**时：用户名/邮箱注册、OAuth 注册都必须携带有效邀请码，否则拒绝
- **关闭**时：保持现状，邀请码可选
- **管理员后台手动创建用户不受限制**

### 2. 充值返利系统（按 quota 比例 + 30 天解冻）
- 被邀请用户**每次充值**都触发返利
- 返利比例可在管理后台动态配置（默认 10%）
- 返利金额按**实际到账 quota** 计算（非人民币金额）
- 仅返利**一级**邀请人
- 充值后 30 天内为「待到账」状态，30 天后自动解冻为「待使用收益」（可转入主余额）
- 配套统计报表（管理员） + 用户邀请明细页面（用户）

### 3. 登录页面优化
- 参考设计稿：`docs/degin/邀请注册以及邀请奖励/返利参考图片/登录页面参考.png`
- 简洁居中卡片布局
- 用户名/邮箱合一输入 + 密码 + 「继续」 + 「忘记密码」
- 「或」分割线下方一排显示三方登录按钮（**支持：GitHub + 邮箱 + 用户名注册**）

### 附加功能：管理员删除用户（独立小任务）
- 管理后台用户列表新增「彻底删除」按钮
- 级联清理：日志、Token、充值记录、返利记录、邀请关系（被该用户邀请的人 InviterId 置 0）
- 用于清理历史无邀请人的用户

## 三、关键技术决策（已确认）

| 决策点 | 方案 |
|--------|------|
| 30 天延迟实现方式 | **方案 B：充值时立即记录返利到 pending 状态，30 天后由定时任务自动解冻** |
| 返利计算基准 | 按实际到账的 **quota** 计算（与货币无关） |
| 返利层级 | 仅一级 |
| 返利上限 | 无 |
| 历史用户处理 | 清理（通过管理员删除用户功能实现），不补返利 |
| OAuth 注册校验 | 限制开启时也校验邀请码 |
| 管理员创建用户 | 不受邀请码限制 |
| 退款处理 | 暂不考虑（后续如有需要再做） |
| 提现功能 | **暂不实现**（前端按钮可显示但禁用或隐藏） |

## 六、风险与注意事项

1. **支付幂等性**：每个支付方式的 `Recharge*` 函数已有幂等逻辑（`Status == TopUpStatusSuccess` 则跳过），返利逻辑必须放在事务**之后**或使用同一事务，避免重复返利
2. **并发控制**：依然使用现有的 `LockOrder/UnlockOrder` 机制
3. **历史 InviterId**：现有用户已有 `InviterId` 字段绑定关系，需求明确「不为历史用户补返利」，但**已绑定关系的用户在新功能上线后充值依然会触发返利**（这是符合需求的）
4. **管理员补单**：`ManualCompleteTopUp` 也应触发返利，避免管理员补单跳过返利
5. **登录页风险**：现有登录页支持 8 种 OAuth + Passkey + WeChat + 2FA，重新布局时需保持所有功能可用
6. **保护项**：CLAUDE.md 第 5 条 — 项目品牌信息「new-api / QuantumNous」严禁修改
