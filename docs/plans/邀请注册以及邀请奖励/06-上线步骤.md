## 二、部署步骤

### 2.1 停机部署（推荐小型部署）

```bash
# 1. 停止服务
systemctl stop new-api  # 或 docker compose stop

# 2. 备份数据库（见上）

# 3. 拉取新代码
cd /opt/new-api
git fetch origin
git checkout llm-link-v1.0
git pull

# 4. 后端编译（如本地编译）
go build -o one-api .

# 5. 前端构建
cd web/default
bun install
bun run build
cd ../..

# 6. 启动服务（GORM AutoMigrate 自动建表 + 加列）
systemctl start new-api

# 7. 查看日志确认启动成功
journalctl -u new-api -f --tail 100
```

**关键验证点**：
- 启动日志中是否有「database migration started」
- 没有迁移失败错误
- `aff_rebate_records` 表已创建
- `users` 表新增 `aff_pending_quota` 列

### 2.2 Docker 部署

```bash
# 1. 拉取新镜像（或本地构建）
docker pull <your-registry>/new-api:llm-link-v1.0

# 2. 重启容器（GORM 自动迁移）
docker compose down
docker compose up -d

# 3. 查看日志
docker compose logs -f new-api
```

### 2.3 滚动部署（多节点）

如果多节点部署：

1. **只让 master 节点先重启**（执行迁移）
2. master 节点启动成功后再重启 slave 节点
3. 配置项 `IsMasterNode` 控制定时结算服务只在 master 运行（见 [02-后端实施计划.md](./02-后端实施计划.md) § 4.3）

## 三、上线后配置

### 3.1 默认行为：所有开关关闭

上线后默认配置：
- `AffRegisterRequired = false`
- `AffRebateEnabled = false`
- `AffRebateRatio = 0.10`
- `AffRebateWaitDays = 30`

**系统行为与上线前完全一致**，不会影响现有用户。

### 3.2 开启返利的灰度策略

**阶段 1（D+0）**：观察期
- 仅部署代码，所有开关保持关闭
- 监控数据库迁移、定时任务启动情况
- 持续 1-3 天，确认无异常

**阶段 2（D+3）**：开启返利
- 管理后台开启 `AffRebateEnabled`
- 设置合理比例（如 0.10）
- 触发一笔小额测试充值，验证返利记录正确创建
- 持续观察 7 天

**阶段 3（D+10）**：开启邀请注册
- 管理后台开启 `AffRegisterRequired`
- 提前在公告/通知中告知用户

**阶段 4（D+30+）**：首批返利解冻
- 30 天后定时任务开始结算最早一批 pending 记录
- 监控结算日志和用户反馈

## 四、监控指标

### 4.1 关键指标

| 指标 | 监控点 | 告警阈值 |
|------|-------|---------|
| 返利创建成功率 | service 日志中 `[CreateAffRebate]` | 失败率 > 1% |
| 定时结算延迟 | 定时任务运行时间 | 单批 > 30 秒 |
| pending 记录积压 | `SELECT COUNT(*) FROM aff_rebate_records WHERE status='pending' AND settle_at < UNIX_TIMESTAMP() - 3600` | > 100 条 |
| 充值流程异常 | 充值日志 | 报错增加 |

### 4.2 推荐 SQL 监控（每天检查）

```sql
-- 每日返利汇总
SELECT
  DATE(FROM_UNIXTIME(created_at)) AS day,
  COUNT(*) AS records,
  SUM(rebate_quota) AS total
FROM aff_rebate_records
GROUP BY day
ORDER BY day DESC
LIMIT 30;

-- 待结算积压检查
SELECT COUNT(*), SUM(rebate_quota)
FROM aff_rebate_records
WHERE status = 'pending' AND settle_at <= UNIX_TIMESTAMP();

-- 数据完整性核对（用户表 vs 记录表）
SELECT u.id, u.aff_pending_quota,
  (SELECT COALESCE(SUM(rebate_quota), 0)
   FROM aff_rebate_records
   WHERE inviter_id = u.id AND status = 'pending') AS computed
FROM users u
WHERE u.aff_pending_quota > 0
HAVING u.aff_pending_quota != computed;
```

## 五、回滚方案

### 5.1 业务层回滚（无需回滚代码）

最简单的回滚方式：**关闭所有开关**

```sql
UPDATE options SET value = 'false' WHERE key IN ('AffRegisterRequired', 'AffRebateEnabled');
```

或在管理后台直接关闭。系统行为立即恢复到上线前状态。

### 5.2 代码回滚

如必须回滚代码：

```bash
# 1. 切回旧版本
git checkout <previous-commit-sha>

# 2. 重启服务
systemctl restart new-api
```

**注意**：
- 新表 `aff_rebate_records` 和新列 `aff_pending_quota` 不会自动删除
- 旧代码不读取这些字段，**保留它们不会有问题**
- 如需彻底清理，参考 [01-数据库设计.md](./01-数据库设计.md) § 六

### 5.3 数据回滚（最坏情况）

如果数据被错误污染（如返利金额计算错误）：

```sql
-- 删除所有 pending 状态记录（未实际转移到 aff_quota 的）
DELETE FROM aff_rebate_records WHERE status = 'pending';

-- 重置用户 aff_pending_quota
UPDATE users SET aff_pending_quota = 0;

-- 已 settled 的记录无法简单回滚，需根据 LogTypeSystem 日志手动核对
```

> - 已有账号的用户可在「个人中心 → 邀请奖励」页面获取自己的邀请链接
> - 通过邀请链接邀请新用户注册，每当被邀请用户充值时，您将获得 10% 的返佣奖励
> - 返佣金额将在 30 天后自动解冻，可划转到主账户余额使用
>
> 感谢您的支持！

### 7.2 常见问题

**Q：为什么充值后邀请人没有立即收到返利？**
A：返利金额会先进入「待到账」状态，30 天后自动解冻为「待使用收益」。

**Q：返利比例可以调整吗？**
A：返利比例由系统统一设定，当前为 10%。已产生的返利记录会保留生成时的比例不变。

**Q：被邀请用户取消账号后，未结算的返利会怎样？**
A：未结算的返利会按原计划继续结算，因为返利已基于实际充值产生。

**Q：邀请人注销账号后，被邀请人的充值还会产生返利吗？**
A：不会。邀请人账号注销后，该绑定关系失效。
